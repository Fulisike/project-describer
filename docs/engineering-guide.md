# 一个 C++ 项目怎么写得专业又好维护

这份说明不讲玄学，讲的是这个项目已经在用、也适合大多数中小型 C++ 工具的做法。

## 先把职责分开

一个 C++ 项目开始时常常只有一个 `main.cpp`。这很正常，但一旦它同时解析参数、扫描目录、读文件、处理编码、拼字符串、写文件，后面改任何一处都会很紧张。

更舒服的分法是：

- `application` 负责“用户想做什么”，例如解析 `-p` 和 `-o`，再安排执行顺序。
- `core` 负责真正的业务动作，例如扫描项目、生成报告。
- `model` 放小而稳定的数据结构，例如文件项和编码类型。
- `utils` 或 `infrastructure` 负责靠近系统的细节，例如文件、字符编码、网络或数据库。

这不是为了目录看起来高级。判断是否该拆开，问一句就够了：将来 GUI 也要用这段逻辑吗？如果答案是“要”，它就不应该被塞进 CLI 的 `main.cpp`。

## 构建别靠手工点按钮

CMake 的价值是把“怎么编译”写进仓库，而不是记在某个人脑子里。这个项目使用了三个关键习惯：

- 明确列出库和可执行文件的源文件，不用 `GLOB` 自动捞所有 `.cpp`。新增文件时多写一行 CMake，却能避免不小心把实验代码编进产品。
- 先建一个可复用的 `project_describer_core` 库，再让 CLI 和测试都链接它。测试因此测到的就是产品代码。
- 把测试开关做成 `PROJECT_DESCRIBER_BUILD_TESTS`，发布构建可以关闭它。

日常命令就是：

```powershell
cmake -S . -B build -DPROJECT_DESCRIBER_BUILD_TESTS=ON
cmake --build build --config Debug
ctest --test-dir build -C Debug --output-on-failure
```

Debug 用来开发和排错，Release 用来发给别人。不要把 `build/` 提交进 Git；它只是本机生成物。

## 测试从行为开始写

单测不是为了“覆盖率数字漂亮”，而是把容易回归的承诺写下来。这个项目的测试覆盖了：参数缺失、UTF-8/UTF-16/UTF-32、二进制排除、无扩展名文本、历史报告排除、重名输出和报告内容。

一个简单的顺序很好用：先写一个能说明预期行为的测试，运行它让它失败，再实现最小改动让它通过。尤其是编码、路径、文件名冲突这些边界条件，测试比手工试一次可靠得多。

测试要小。比如“扫描器忽略旧报告”不需要真的启动命令行程序，只要建一个临时目录、放四个文件、调用扫描器、检查结果即可。这样失败时能很快知道是哪一层出了问题。

## 依赖要有边界

优先用标准库和稳定的系统 API；确实需要第三方时，说明它解决什么问题、怎么升级、怎么构建。`cxxopts` 在这里仅负责命令行，不让它渗入扫描或编码层。将来换参数库，影响就局限在 `application/command_line.cpp`。

字符编码特别值得克制：自动猜编码永远有不确定性。当前做法是把检测和转换放在一个独立适配器中，报告统一为 UTF-8。这样当遇到罕见旧编码时，可以补一个“用户指定编码”的功能，而不是在扫描器里堆越来越多的例外。

## 提交前的小检查

- `cmake --build` 是否干净通过？
- `ctest --output-on-failure` 是否通过？
- 用一个真实的小项目跑一次 CLI，检查输出路径、中文路径和报告内容？
- 新增的行为有没有对应测试？
- README 是否告诉新同事怎样构建、怎样运行？

做到这些，这个项目不一定华丽，但会很好接手、很好改，也不容易在几个月后反过来为难自己。
